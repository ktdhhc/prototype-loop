# 组件库采样原型

> 阶段 1 在组件库未定时使用；已有视觉依据且用户选择“试画对照”时也使用。先核对已有产品与视觉依据，再按 `prototype` 技能制作可切换原型。

## 为什么用看的

"用哪个组件库"是视觉判断——密度、圆角气质、字阶渲染、语义色的味道——用问的问不准，必须看真的。这正是 prototype 技能哲学的标准应用：一次性代码回答一个问题，"这家库顺手吗？"

## 一条变体轴：候选组件库

- 每个变体呈现同一份 7–10 组元素、同一份示例数据；候选库通常为 2–4 个。按 `prototype` 技能当前的切换方式展示。
- 选择“试画对照”时，将现有视觉依据作为基准参照；只比较组件呈现差异，不顺带改变内容清单、页面结构或产品文案。

历史教训（轴混淆）：变体之间若同时差库与差元素清单，选择被污染。各库渲染**同一份清单**是本原型的锁轴。

## 元素清单：核心 7 组 + 领域加选（凑足 7–10）

| # | 组 | 必选理由 |
| --- | --- | --- |
| 1 | 按钮族 | 主 / 默认 / 危险 / 加载 / 禁用——气质差异最直观 |
| 2 | 表单 | 输入 / 选择器 / 日期 / 校验错误态——日常接触面最大 |
| 3 | 表格 | 紧凑密度、排序、行操作——管理台的事实标准 |
| 4 | 反馈 | 弹窗 / 抽屉 / 消息 / 确认——交互骨架 |
| 5 | 排版与数据 | 字阶层级、mono 数字对齐、标签 / 徽章 |
| 6 | 导航与层次 | 侧栏 / Tab / 面包屑 / 折叠——界面骨架的气质所在 |
| 7 | 空态与状态 | 加载骨架 / 空态 / 错误呈现——各库差异大且难事后换 |
| +8..10 | 领域加选 | 由目标产品的域决定：树 / 级联（配置类）、上传（内容类）、步骤条（流程类）、密度对照（数据密集类）等 |

加选组依据当前已知的产品事实和预计会使用的组件选择；此时界面访谈尚未开始。

## 制作规则

1. **采样范围**：候选库通常不超过 4 个；每个候选库都呈现同一份 7–10 组元素后再比较，不用半成品代替最终采样。
2. **真实感数据**：示例内容贴近目标域（prototype 技能规矩：不用占位废话）——看"查询候选人 C2026-0358"和看"Text"的判断质量完全不同。
3. **同一数据贯穿**：各库渲染同一份示例数据、同一份元素清单，差异只剩库本身。
4. **一次性**：采样原型在完成选型后按 `prototype` 技能的当前要求留存证据，不混入正式页面。
5. **遵守视觉依据**：有现成设计约束时，采样的间距、字号和语义色均须与之对齐；差异交用户裁定。

## 结论处理

- 单选一个库 → 记录选型理由，经用户确认且符合项目文档写入规则后再同步产品技术栈说明。
- **混合结论是正常产出**（“A 库的按钮 + B 库的选择器”）→ 如实记录组合及维护代价，供后续视觉依据与组件样式决策核对；不自动改写既有文档。
- 用户判定都不合适 → 允许换一批候选重采一轮，或决定自绘（自绘意味着 DESIGN.md 需承载完整组件规范，工作量在层循环中显著上升——向用户说明此代价）。

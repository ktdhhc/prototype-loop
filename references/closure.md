# 收口

> 阶段 6 执行。前置：所有层冻结、账本完整。产出：视觉依据变更的确认结果、清理后的交付页及页面设计与接线说明。

## 6.1 决策变化总结 → 同步 DESIGN.md

层循环里凡是**改变视觉权威**的决策都已标 `ΔDESIGN`；收口第一步就是把这份清单变成 DESIGN.md 的修订提案。

1. 扫账本全部 `ΔDESIGN` 标记，逐条核对 DESIGN.md：
   - DESIGN.md 已有且一致 → 不动；
   - 冲突（如页面实践中发现既有 Don't 被违反、或既有条款与定稿矛盾）→ 提请用户修订；
   - 缺失（如经验证的容器内对齐规则、状态的非颜色可访问名称）→ 建议补条目。
2. **逐条经用户确认后才写 DESIGN.md**。DESIGN.md 是基线文档，agent 只负责把决策变化摆到桌面上并起草措辞，写入权在用户。
3. 回写完成后在账本标记每条的去向（"已并入 DESIGN.md §X" / "用户裁定不回写"）。

这一步存在的理由：正式 UI 开发读到的视觉权威是 DESIGN.md；层循环改出来的东西若只留在过程账本里，权威与实物就会分叉。

## 6.2 清理清单

逐项核对，全部完成才算收口：

- [ ] 核对文件所有权与工作区状态后，清理原型专用的占位、切换控件、落选变体和附属样本；保留仍用于演示的工具并明确标注
- [ ] 将交付页面中的临时命名、注释与开发环境门控整理为实际交付语义；生产构建能进入该页面
- [ ] 对没有正式接口的能力清楚标注“规划中”“只读”或“演示数据”，并说明演示状态与真实持久状态的区别
- [ ] 抽查标题层级、图标按钮可访问名称、非颜色状态信息及键盘路径
- [ ] 运行项目适用的类型检查、构建和主要交互路径；记录验证结果，不假设某种前端框架
- [ ] 核对每条跨层待办的去向：已解决、交付说明中的未决问题或经用户确认移出范围
- [ ] 若用演示数据呈现列表和运行过程，确认它足以覆盖定稿形态且能支撑主路径

## 6.3 页面设计与接线说明

以下九节是管理台页面的交付示例，按当前项目的实际页面与文档权威调整。目的是让正式开发不必遍历过程账本，就能拿到已定决策、接缝与边界；说明文档不取代项目的正式领域与规格依据。

```markdown
# <页面名> · 设计与接线说明

> 用途：正式 UI 开发的设计与接线参考；与当前项目的权威文档冲突时，先核对并解决冲突。

## 1. 定位
这一页是什么；引用当前项目实际采用的领域依据与边界。

## 2. 页面结构
结构图（ASCII 即可）+ 各区域一句话职责。

## 3. 已定稿的设计决策（逐层表）
| 层 | 决策 | 关键理由 |
—— 直接从账本各层定稿记录提炼，一行一层。

## 4. 功能清单
按对象分组（如：案例集级 / 案例级 / 批次级 / 查看），每条一个可验证的行为。

## 5. 数据接缝与接线要点
| 用途 | 当前数据或命令接缝 | 正式接缝或缺口 |
+ 若有运行流程，写明必须保留的顺序、状态与失败语义。

## 6. 状态与边界
每种状态一行：呈现方式 + 设计依据。保留演示样本时，注明其对真实数据的影响。

## 7. 设计纪律
本页沉淀、对后续页面同样适用的规则（对齐 DESIGN.md；若 6.1 已回写则此处只引用）。

## 8. 接线时仍未解决的问题
编号列出：领域缺口（需后端）、未定项、演示手段的下线条件、发现并修复的数据缺陷。
—— 这是给后端与下一位开发的交接重点。

## 9. 关键文件
| 文件 | 职责 |
+ 过程账本的位置（注明“非正式规格”）。
```

# 层循环（Layer Loop）

> 阶段 5 执行。每层六步：锁轴原型 → 渲染验收与初选 → grilling 决策核对 → 确认本层结论 → 固化基线与清理 → 冻结停层。外部依赖：`prototype` 技能（变体切换、悬浮条规范）、`grilling` 技能与逐题提问工具。

## 第 1 步 — 锁轴原型

先按主文件的“实际加载契约”核对 `prototype` 已实际加载，并获取当前 UI 分支要求的材料；未就绪则停在本步。账本注明本层使用的加载依据与分支材料，再制作原型。

本层只变本层那一轴；其余轴全部锁死为已冻结的定稿（上游层）或空位占位（下游层）。

**规则**

- **锁轴是前提不是优化**。历史教训：变体 B（紧凑两栏）与变体 C（舒展抽屉）同时差拓扑和密度，用户的选择被污染（"倾向 B 又舍不得 C 的密度"），整轮返工。开建前先写下"本层变体之间唯一的差异是什么"，写不出就回拆层。
- **空位占位块**：未决定的内容用统一的占位组件，让用户看到预留范围而不引入具体做法；归属层只记在账本，不把内部流程标签渲染为产品内容。
- **占位分两种，视觉可区分**：本层未定的脚手架（决定后逐层替换，收口检查残留）与"无真实接口"的诚实占位（长期保留，用标注青 + 可见文字）。
- **真实链路优先**：功能原型尽量复用项目已有命令与可运行数据，尤其是运行进度、阻断和取消；需要合成状态时明确标为只读演示样本。组件库采样只比较视觉，可用静态示例。
- **变体切换**：按已加载 `prototype` 技能的当前 UI 变体约定制作可切换原型。一次只比较本层决策点；本层收尾移除落选分支和旧切换入口，仍有用途的工具按第 5 步处理。
- **样本态**：当真实数据难以同时呈现多种状态（空 / 加载 / 失败 / 阻断 / 取消残留 / 超长）时，建一份**只读演示样本**（不写库、页内标注"状态样本"），让用户不用真跑就能对照各状态。历史教训：内存 mock 刷新即空，用户打开页面全是空白，"完全没有办法选择"。
- **从第一步遵守当前项目的视觉纪律**：用已选组件库的推荐组件、尺寸与间距；检查容器内文字留白、既有字阶及图标按钮的可访问名称。案例集页曾因忽略这些约束而反复返工；其他项目按各自视觉依据判断。

## 第 2 步 — 渲染验收与初选

原型可点后交用户在真实浏览器里看（生产构建照常可用的前提下，dev 环境走查）。用户的每条反馈三分归类：

| 反馈类型 | 处理 |
| --- | --- |
| 违反当前项目既有设计约束或出现可见实现错误 | **当场修**——这不是本层的新设计决策 |
| 本层未定的决策点 | 进 grilling 问题池 |
| 属于别的层的输入 | 记跨层待办，不当场做（"进度卡展开进会话"在骨架层提出 → 记到动作层） |

渲染验收是信息量最大的环节——大部分关键修正（对齐、重复、密度、信息命名）来自用户看真实页面，而非脑内推演。宁可多轮验收，不替用户想象。

记录用户初选及已表达的理由。**选定变体只表示方案偏好**，尚不表示 grilling 完成、本层冻结或下一层获准启动。

## 第 3 步 — grilling 决策核对

读取 [逐题对齐](questions.md)，按主文件的“实际加载契约”核对 `grilling` 已实际加载，原指令不可用时先重新加载；未就绪则停在本步。依据原技能执行本层核对，检查所选方案在本层范围内仍有哪些会改变做法的取舍、代价或边界，把加载依据、核对结果与逐题回答写入账本。

**每层必须核对，可以零提问**。零提问须满足逐题对齐中的证据要求；用户没有主动提出分歧或已经选定变体，都不足以单独证明没有未定决策。

## 第 4 步 — 确认本层结论

展示本层定稿摘要：方案、关键理由与代价、明确延后事项及去向，请用户确认共同理解。已有的明确回答可作为依据，不重复问已解决的决定；仅有原型初选或“继续”不代替对这份结论的确认。

grilling 若改变了原型，先落实改动并重新渲染验收，再确认结论。确认后将本层标为“待收层”；涉及视觉依据的决策标 `ΔDESIGN`，随后整理产物。

## 第 5 步 — 固化基线与清理

用户确认后，将本层定稿固化为下一层的唯一基线。先核对文件所有权、工作区改动和引用关系，再逐项处理：

| 产物 | 处理 |
| --- | --- |
| 定稿方案 | 保留并成为默认可运行路径；后续层只在此基线上增加本层差异 |
| 本层落选变体及其专属代码、样本、样式和路由 | 从活跃原型中移除；清掉专属导入、分支和旧切换选项，不能只隐藏入口 |
| 定稿仍使用的共享组件、演示样本及下游占位 | 保留，说明用途；落选方案使用过它们不构成删除理由 |
| 变体切换工具 | 移除旧层比较入口；工具仍需复用则保留骨架，下一层开始后再添加新选项，否则移除 |
| 历史证据 | 决策、理由与推翻原因留账本；按项目与 `prototype` 的留存要求保存必要证据，但不继续挂在活跃页面；提交、建分支等操作仍须相应授权 |

存在用户或并行改动、共享用途不明的产物先停下确认，不强删。账本逐项记录保留、移除或暂留及原因；无法安全处理的落选残留是收层阻碍，本层保持“待收层”，报告后等待解决，不自动推进。

整理后检查定稿页可打开、主交互可用、落选分支与旧切换入口已退出活跃原型；运行与改动相称的项目检查（如类型检查或构建），记录命令、结果与阻碍。这里只验证本层整理没有破坏基线，不代替最终收口的完整走查。

## 第 6 步 — 收层闸门、冻结与停层

账本中以下四项齐备才标为“已冻结”：

- [ ] `prototype` 与 `grilling` 的实际加载依据、所需分支材料已记录；grilling 核对完成，有逐题结果或有据可查的零提问依据。
- [ ] 用户已确认本层结论；延后事项有明确去向。
- [ ] 定稿基线已固化，落选产物已清理，保留项有用途说明。
- [ ] 整理后的适用验证通过，无未解决的收层阻碍。

向用户输出：**本层定稿摘要 + 核对与清理验证结果 + 下一层预告（做什么、为什么现在做）**。随后停下，用户放行才启动下一层。账本分别记录结论确认和推进授权。

- 用户说“B，继续” → 记录 B 为初选及推进授权，先完成第 3–5 步并通过收层闸门；需确认结论或补决策时仍等待回答。授权不豁免任何步骤。
- 用户显式授权连续推进（“后面几层连着做”）→ 账本记授权范围；每层仍须核对、确认结论、整理和验证，超出授权范围即停。
- 用户在停层期插入新输入 → 先归类：属于已冻结层 → 回退重开该层（见下）；属于未来层 → 记跨层待办。

## 回退协议

用户推翻某个已冻结的决策，或在渲染验收中暴露结构理解错误：

1. **回到该层决策前**，找出仅为错误方案服务的变体、附属原型和样本。核对所有权与工作区状态后清理；对存在用户或并行改动的文件先停下确认，不在错误结构上叠补丁。落选代码已清理时，根据账本与必要证据重建，不以保留活跃落选分支作为回退前提。
2. 账本记录：推翻原因、用户原话要点、新方向。
3. 重做该层原型，重新走六步与收层闸门。
4. 下游层若已建立在被推翻的结论上 → 一并标记回退，按闸门流程重新确认分层表（通常无需重拆层，只需重做受影响的层）。

推翻是正常事件：在账本保留决策变化的原因，交付说明只保留当前结论与仍未解决的边界。
